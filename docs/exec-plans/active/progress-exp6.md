### ⛔ 类别均衡分配：4 条错误路线（已放弃，别再走）
| 版本 | 思路 | 结果 |
|:--|:--|:--|
| v1 | 只按**图片数**均衡（**当前采用**） | val 类1 偏少：in_hand 10447 : on_ear 2086（83:17） |
| v2 | 取各指标**相对欠额的最大值** | 被大类组主导、正反馈 → val 只剩 **657 张**、类1 占 1.6% |
| v3 | 只盯**类1 比例**偏离 | 类0 被压到 val 6.7%（只是把偏斜从一类换到另一类） |
| v4 | **局部搜索 + 配对体积守恒** | 约束过紧，收敛到 train 92% 的更差解 |
| v5 | 各组填"最欠额折"（各类按规模加权） | 仍未配平；切除旧代码时留下孤儿片段，**最终 `git checkout` 回退到 v1** |

**结论与取舍**：组是不可切分的原子单位（同源图必须同折），此约束下强行配平类别会顾此失彼。
v1 的偏斜（val 类1 约占 17%）**用逐类指标化解**——评估时同时报总体 mAP 与各类 AP，
并在报告里注明各折类别构成。**这条路已花掉约 30 分钟，别再尝试。**


### 当前各折实测（2026-10-01）
```
train 图 16752  框 24426  in_hand 13620  on_ear 10806  负样本 1617 (9.7%)
val   图  3589  框 12533  in_hand 10447  on_ear  2086  负样本  299 (8.3%)   ← 偏斜
test  图  3589  框  5730  in_hand  3684  on_ear  2046  负样本  338 (9.4%)   ← 偏斜
```
**偏斜原因**：分配时按"每组图片数"投给最欠额的折，而 `in_hand` 密集的组集中落在 val。
**修法**：改成按**类别计数加权**的欠额度量（或先按类分层再分配）。

## 踩过的坑（勿重犯）
1. **内存/耗时**：对 2.4 万张图做"每张 × 2500 次最近邻"= 千万级距离计算，会跑到超时。**改用精确哈希表 O(n) 匹配**。
2. **缓存键**：用 `split|stem` 会因**同名文件并存于原始 train 与 val** 而互相覆盖（统计只覆盖 15186/23930）。必须用**完整路径**。
3. **探测自动工具**：哈希去重必须先自证有鉴别力——本次用"同源对 vs 异源对"距离分布对照（同源中位 0 / 异源中位 72）。
4. **同一文件连续两次 edit** 会因第二次的 old_string 匹配到被改过的内容而失败或覆盖，**改完先读一遍再改第二次**。
5. **PowerShell here-string 里的 Python f-string** 容易被当子表达式解析；**一律写成 .py 文件再跑**。
