### 错误 #012 - 2026-09-30
- **现象**：为静态 Demo 压缩模型体积做 int8 量化，量化后的模型**能加载、能推理、不报错，但结果全错**——框回归正常，类别分数恒为 0.000，检测数从 N 变成 0。
- **原因**：YOLO11 的检测头（分类分支 + sigmoid + Concat）对激活量化极不友好。实测四种配置全部失效：`QuantFormat.QDQ/QOperator` × `per_channel=True/False`；且 `quantize_dynamic` 另一条路直接产 `ConvInteger`，ONNXRuntime 的 CPU EP 与 WASM EP 都没有该算子实现（`NOT_IMPLEMENTED`）。ONNX Runtime 官方对此类模型有明确提示：`Please consider to run pre-processing before quantization`（需要一个带预处理层的导出模型）。
- **建议修复**：**放弃 int8，静态 Demo 只发布 fp32 ONNX**（yolo11n 10.1 MB，对比：yolo11s 36.2 MB 也偏大，故网页版只放 nano）。`src/models/export_onnx.py` 的 `--int8` 现在带**自检**：量化后实跑几张小图比对检测数与类别分数上限，不合格就直接删掉产物并以返回码 3 退出——不允许"能加载但结果是错的"模型留在仓库里。
- **状态**：已知限制（量化在本模型上不可行，已用自检兜住）

### 错误 #013 - 2026-09-30

- **建议修复**：新增 `src/utils/helpers.imread_unicode()`（`np.fromfile` + `cv2.imdecode`），新代码统一走它；导出脚本与示例图生成脚本已改用。
- **状态**：已修复

### 错误 #014 - 2026-09-30
- **现象**：静态 Demo 的浏览器自检一开始"全绿"，但把 `letterbox` 的灰边补偿 `- pad[0]` **故意删掉后自检依然 PASS** —— 也就是说那条断言当时没有鉴别力。
- **原因**：最初几张示例图全是 640×640 方形图（letterbox 不产生灰边，`pad` 恒为 0），那段代码根本没被执行；补了一张 640×400 横图后仍 PASS，因为**横图只让 `pad[1] ≠ 0`，被破坏的是 x 轴**。
- **建议修复**：示例图必须同时包含**横图（覆盖 pad[1]）与竖图（覆盖 pad[0]）**，并把这条约束写成 `src/models/gen_demo_fixtures.py` 的**自校验**（缺任一种就拒绝生成基准、返回码 5）。补上竖图后，同样的破坏立刻被自检抓住（minIoU 0.999 → 0）。
- **状态**：已修复
- **教训（可复用）**：自检的价值不看"是否 PASS"，而看"**改了该抓的东西它会不会红**"——新写的断言必须先用一次故意破坏证明它有牙齿。

### 错误 #015 - 2026-10-01
- **现象**：线上 Demo 实际使用时**频繁把人脸检测成手机**（用户报障原话：「检测效果不佳，经常出现把人脸检测为手机的情况」）。实测复现：40 张「标注中无手机」的验证图上，conf≥0.25 有 33 张冒出手机框（最高分 0.86），**conf≥0.70 仍有 25 张**；把误检框画出来一看，扣的全是**人脸**（安全帽脸、口罩脸、低头看手机时的人脸上半部）。
- **原因**：**训练标注本身把脸标成了手机**。合并后的 18,800 张训练图里，**42.9%（8,059 张）含至少一个"大手机框"**（边长 >35% 图幅）；train 共 24,993 个 `cellphone` 标注中，边长 >25% 的占 77.2%、>50% 的占 5.9%，而 `People using cellphone` 的中位边长仅 13.5%——**"手机"比"拿着手机的人"标注得还大**，语义倒挂。根因是 4 个 Roboflow 数据集对"手机"的定义不一致（有的标手机本体、有的标头部/手持区域），合并时**没有统一标注口径**，且合并脚本 `merge_datasets.py` 未入库、无法追溯。
- **关键影响**：val 集同源污染（25.1%，303/1730 张含大框），所以 **mAP@50=0.73 是虚高的**（照着坏标注考坏标注），**不能作为"检测效果好"的证据**。
- **已排除**：类别映射无错（data.yaml→权重内嵌 names→app.js→fixtures 全链条 0=使用手机的人、1=手机）；调阈值救不了（>0.85 仍有 3/40 漏网）；误检框与人物框 IoU 几乎全为 0，说明是**专属人脸触发模式**，而非"把人判成手机"。
- **建议修复**：① 逐数据集审计标出口径、定位污染源；② ~~清洗——建议直接丢弃大框~~ → **该建议已被错误 #016 的审计证伪，见下**。
- **状态**：已定位，处理方案见 #016（污染范围比本条目初判的更大，"按尺寸丢大框"行不通）

### 错误 #016 - 2026-10-01（#015 的后续审计：污染范围被严重低估）

对 #015 做逐档可视化审计后，结论**推翻**了 #015 里"丢弃大框即可清洗"的建议：

**审计方法与自证**
- 探针自证：用 3 个源数据集的 9 张已知图回溯索引，**9/9 命中** → 确认反查探针有鉴别力，下面的"0 命中"才是真实结论。
- 逐尺寸档出图人工核对：`small≤15%` / `mid 15-35%` / `big 35-55%` / `huge>55%` 各 30 张。

**发现 1：污染覆盖全部尺寸档，没有干净子集**
- `big 35-55%` 档：**清一色是"红框扣头部 + 绿框扣真手机"并存**——同一张图里 `cellphone` 和 `People using cellphone` 各标了一遍，前者扣脸。
- `small ≤15%` 档（原本以为最干净）：**仍有人脸误标**（如"框扣在路人脸上，而该路人手里明明拿着手机却没被框"）。
- ⇒ **污染与真实手机标注的尺寸分布完全重叠**，"按尺寸丢大框"分不开。

**发现 2：`only_cellphone` 子集同样是脸**
重组集 train 里结构分布：`both` 8,347 / `only_cellphone` **10,394** / `only_person` 11 / `empty` 48。
抽样 `only_cellphone` 15 张——**框的仍全是头部/人脸**（e=0.20~0.59），不是"另一套干净口径"。
⇒ 不能把"只有手机类的图"当干净数据救回来。

**发现 3：合并来源无法追溯**
- 重组图文件名被重新哈希（`012eEqi4…`），**来源信息未保留**；合并脚本 `merge_datasets.py` **已不在盘上**（不是未入库，是没了）。
- 用 dhash 感知哈希把重组 train 的 18,800 张与盘上全部源数据集（4,352 张）对撞：**精确哈希 0 命中**（探针已自证可用）。
- 更关键：核对各源数据集 `data.yaml` 发现，`University-Outdoor / ver2 / ver3 / School v1 / college / school` 的类别是 **door / elevator / stair / Window / Tree / helmet / bicak…——根本没有手机类**。
  ⇒ **current-plan 自述的"合并 University-Outdoor + ver2/ver3 + School v1"与实际不符**；真实的合并来源既未知也不在盘上。

**结论：22,879 张重组数据集整体不可用**，全库 images 都含"人脸被标成 cellphone"，无法通过过滤/采样抢救。

**唯一确认干净的数据**：原始 **Smart School v5（141 张）**——红框精准扣小手机、绿框扣在人身上，无一处扣脸；`cellphone` 框中位边长仅 **0.037**（重组集是 0.24，差 6.5 倍，两套口径截然不同）。局限：仅 141 张、96 训练图、单场景（教室监控）。

**建议修复（取代 #015 的方案）**：
1. **放弃在重组集上清洗**——污染是全库级、与真标注同尺寸分布，清洗成本高于重做。
2. 二选一：**①** 用干净的 Smart School v5 重训一个"诚实、小而可靠"的演示模型（mAP 必然远低于虚高的 0.73，但可信，且能讲清"发现问题→修数据→重训"的工程闭环）；**②** 重新从 Roboflow 取一套**口径一致**的手机检测数据集重做（需人工抽查确认，勿再盲合）。
3. 无论走哪条，都要在 `src/data/` 加**标注审计闸门**（尺寸分布 + 类别共现 + 抽样出图），并**把合并脚本入库**，杜绝再次哑合。
- **状态**：待处理（审计已完成，等待开发者选择路线）

### 错误 #017 - 2026-10-02
- **现象**：用干净数据（`phone_usage_split`，in_hand/on_ear 两类）重训 **40 轮**后，`Precision = 0.6934`，**未达设定的 0.80 达标线**（差 0.107）。训练本身健康：mAP@50 0.3646、cls_loss 单调下降到 0.71、末 20 轮 P 在 0.63–0.74 波动。
- **原因（三条，按影响排序）**：
  1. **目标尺度/域差异**（主因）：训练集 `phone_usage_split` 主要来自 COCO 近景/自拍（框中位边长 0.05~0.5），而目标场景"教室远距离小手机"的标注框边长中位仅 **0.037**（640 输入下约 24px）。模型没学会该尺度 —— 在 Smart School v5 教室图上与真值手机 **IoU>0.1 命中 0**。
  2. **数据集自带负样本存在漏标**：300 张 `*background_negative*`（标注文件为空）图上，疑似误报的 4 张经**放大目视**确认**画面里真的有手机**（手握/竖握），属数据漏标而非模型误报 —— 这会同时压低 Precision 的上限。
  3. **训练未收敛**：只跑 40 轮，第 33 轮 P 达 0.7428 后仍在波动。
- **已排除/已证伪**：
  - ❌ **"提高推理 imgsz 就能救小目标"**（我 2026-10-01 曾据此建议）：实测**相反**——教室图上 `imgsz=640 → 34 框`、`960 → 16`、`1280 → 15`，放大后更差（训练分辨率是 640，改尺寸造成尺度错配）。**该建议已撤回**。
  - ✅ **提高推理阈值可行**：P 随阈值单调上升，**conf=0.50 时 P=0.8251（达标）**，代价是 R 从 0.395 降到 0.352。完整对照表见 `runs/_diag/threshold_table.md`。
- **建议修复**：① 部署口径把 conf 设为 **0.50**（P 达标，R 可接受）——这是零训练成本的达标路径；② 若要**治本**：补"教室/远距离监控视角、小目标尺度"的训练数据（当前数据集缺这一档）；③ 清洗 `background_negative` 的漏标（补标或剔除）；④ 续训 40 轮（须先解决 checkpoint 被剥离的问题，见 #018）。
- **状态**：已定位；① 可立即落地，②③ 需新增数据

### 错误 #018 - 2026-10-01
- **现象**：40 轮跑完后想"补到 80 轮"，用 `--resume` 启动后进程**立即崩溃**：`AssertionError: ...weights\last.pt training to 80 epochs is finished`
- **原因**：训练**收尾阶段** `last.pt` 被 `strip_optimizer` **剥离成推理权重** —— 实测 `epoch = -1`、`best_fitness = None`、优化器状态为空。而 ultralytics `resume_training()` 要求 `0 < ckpt[epoch]+1 < self.epochs`；剥离后 `start_epoch = 0` → 断言失败。
  （同一文件在训练进行中读还是 `epoch=32 / best_fitness=0.19137`，是收尾时被剥掉的；且我此前只把 `train_args.epochs` 从 40 改成 80 —— **改目标值救不回被剥离的训练状态**。）
- **建议修复**：① 要支持续训，必须在训练中/收尾前**另存一份未剥离的 checkpoint**（用 `save_period` 定时存，或训练结束前后手工复制 `last.pt`）；② 判别"能否续训"只看一条：**ckpt 里 `epoch >= 0` 且带 `optimizer` 状态**；③ 已剥离时只能 **warm-start 重训**（权重在、优化器动量与学习率调度重置，与续训不等价）。
- **状态**：已定位（机制限制，`--resume` 保护已加：传绝对路径、找不到即报错退出，见提交 `51b594e`）
