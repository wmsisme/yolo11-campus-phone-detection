## 2. 项目背景与应用场景

### 背景

随着智能手机的普及，"**边看手机边做别的事**"成为普遍现象：课堂上有学生低头刷手机，影响教学秩序；
考场上、驾驶中、生产线上，手机使用同样是安全与管理的关注点。传统的人工巡查效率低、覆盖面有限，
难以实现全天候监控。计算机视觉技术（特别是目标检测）为**自动化识别"手机正在被使用"**提供了可行方案。

> **与最初设想的差异（如实说明）**：项目最初定位"校园场景"，但可用的**干净标注数据**来自通用
> 手机使用场景（COCO 派生的手机/手持/贴耳标注），**不含校园专用数据**。因此最终交付的是
> **通用场景的「手机使用状态检测」**，校园只是其应用场景之一——**不宣称在校园远距离监控场景下有效**
> （该尺度的限制见第 14 节）。

### 应用场景

1. **课堂教学辅助**：教师上传课堂照片，检测是否有学生在用手机（**近景**可用；远距离见第 14 节限制）
2. **考试/会议纪律辅助**：识别画面中正在被使用的手机
3. **通用内容审核与统计**：批量图片中"手持/贴耳手机"行为的自动识别与计数

### 为什么这是一个有价值的应用

- "手机使用行为"有真实的识别需求（教育、考场、安全），且**比单纯"检测手机"更难**
  （要区分"在用"与"放在桌上"）
- 目标检测技术成熟，可落地性强；纯前端即可运行，**无需服务器、不上传用户图片**

## 3. 任务类型

**目标检测 (Object Detection)**：对输入图片自动分析，检测出**正在被使用的手机**，分两类使用状态：
**`in_hand`（手持手机）** 与 **`on_ear`（贴耳手机）**，输出检测框位置、类别和置信度。

> **口径变更说明（2026-10-02）**：最初按「使用手机的人 (People using cellphone) + 手机 (cellphone)」两类设计，
> 但①可用的**干净**标注数据只标了手机本体、**没有"人"的框**；②原有的重组数据集被查出**标注污染**
> （大量"人脸被标成 cellphone"，导致模型把人脸判成手机，真实负样本误报率 67.7%）。
> 因此改为检测**使用状态**——**框出手机即代表"此处有人在用手机"**，不会圈出整个人。

## 4. 输入输出说明

### 输入

- **类型**：JPG / PNG 格式图片
- **分辨率**：自动适配训练尺寸 640×640
- **来源**：训练用 `phone_usage` 数据集（COCO 派生 + 增广，本地保存不入库）；推理用用户上传图片

### 输出

- **检测框列表**：每个检测框包含类别、置信度、位置坐标 (x1, y1, x2, y2)
- **统计报告**：各类别数量、平均置信度、检测明细
- **标注图片**：在原图上绘制检测框和标签

## 5. 模型与技术路线

### 技术路线

采用 **YOLO11**（You Only Look Once 第 11 代）作为核心检测模型。YOLO 系列是单阶段目标检测器的代表，在速度与精度之间取得了优秀的平衡。

### 模型选择理由

| 对比维度 | YOLO11 | Faster R-CNN | RT-DETR |
|---------|--------|-------------|---------|
| 检测速度 | 最快（单阶段） | 较慢（两阶段） | 中等 |
| 精度 | 高 | 高 | 很高 |
| 训练难度 | 简单（ultralytics 封装） | 中等 | 中等 |
| 数据增强 | 内置丰富增强 | 需手动配置 | 有限 |
| 部署便利性 | 一站式训练/导出/部署 | 较复杂 | 中等 |

**选择 YOLO11 的核心理由**：
1. ultralytics 框架提供完整的训练/验证/推理/导出 Pipeline，减少工程代码量
2. 内置 Mosaic、HSV、翻转等数据增强，在中小规模数据集上即可收敛
3. 提供 nano/small/medium 多个变体，便于多组实验对比

### 数据增强策略

| 增强方式 | 参数 | 作用 |
|---------|------|------|
| Mosaic 拼接 | 1.0 (开启) | 4 张图拼 1 张，丰富背景 |
| HSV 抖动 | h=0.015, s=0.7, v=0.4 | 色彩变化，提升光照鲁棒性 |
| 水平翻转 | 0.5 | 对称扩充 |
| 尺度缩放 | 0.5 | 多尺度训练 |
| 平移 | 0.1 | 位置变化 |

- 分析旧项目（CLIP+BLIP-2 图文检索）存在的根本问题：YOLO 目标检测标注被强行用于检索任务，Recall@5 仅 0.0065

### 阶段二：基础设施搭建

- 备份旧项目 → 创建新目录结构 → 重写 requirements.txt
- 实现 7 个核心模块：数据准备 (dataset.py)、训练脚本 (train.py)、推理检测 (detect.py)、Web 前端 (app.py)、工具函数 (helpers.py + metrics.py)
- 编写 6 类冒烟测试

### 阶段三：第一轮训练实验（Smart School v5, 141 张）

- exp0 (yolo11n, 100 epochs): mAP@50=0.30
- exp1 (yolo11s, 100 epochs): mAP@50=0.29
- exp2 (yolo11m, 150 epochs): mAP@50=0.25 — 大模型反而更差，过拟合
- **关键发现**：数据量太小，模型规模和数据增强无法弥补

### 阶段四：数据集重组

- 从 Roboflow 下载 University-Outdoor、University ver 2/3、School v1 共 4 个额外数据集
- 编写 merge_datasets.py 统一类别映射（person→person, cellphone→phone 等），生成重组数据集
- 最终数据集规模显著增加（22,879 张）——**但后续审计发现该数据集标注被污染，已整体弃用（见阶段七）**

### 阶段五：第二轮训练实验（重组数据集）

- exp3 (yolo11n, 早停 61/100 epochs): mAP@50=**0.73**, mAP@50-95=**0.50**
- exp4 (yolo11s, 100 epochs): mAP@50=**0.73**, mAP@50-95=**0.51**, Recall=**0.88**
- exp5 (yolo11m): 训练中断，未完成
- ~~**关键成果**：mAP@50 从 0.30 跃升到 0.73，成功达到 0.70 质量目标~~
- **⚠️ 上述结论已于阶段七被推翻**：0.73 属于**标注污染下的虚高值**，不能作为效果好的证据

### 阶段六：Harness 文档与最终报告

- 重写全部 11 个 Harness 文档
- 填写最终报告 16 个部分
- 整理实验数据、代码和文档准备提交

### 阶段七：验收发现标注污染 → 换干净数据重训（exp6）★本项目的关键转折

**起因**：在线上 Demo 实测时发现「**经常把人脸检测为手机**」。

**排查（量化复现）**：
- 40 张"无手机标注"的验证图上，conf≥0.25 有 33 张冒出手机框（最高分 0.86），**conf≥0.70 仍有 25 张**
- 可视化确认误检框**全部扣在人脸**（安全帽脸、口罩脸、低头看手机时的人脸上半部）
- 审计标注发现**铁证**：训练集 24,993 个 `cellphone` 标注中，**边长 >25% 的占 77.2%**，
  而「People using cellphone」的中位边长只有 13.5%——"手机"比"拿着手机的人"标得还大（**语义倒挂**）
- 42.9% 的训练图含这种大框；验证集同源污染 25.1% ⇒ **mAP@50=0.73 是"照着坏标注考坏标注"**

**结论**：不是训练不够，是**训练标注本身有毒**；22,879 张重组数据集**整体不可用**（污染覆盖全部尺寸档、
来源不可追溯，详见 `tech-debt-tracker.md` #016）。

**处置（经确认后执行）**：
1. **换干净数据**：`phone_usage` 数据集（train 16752 / val 3589 / test 3589），
   并用**感知哈希 + 并查集**按源视频重切，消除同源帧跨 split 泄漏（**跨折同哈希 = 0**）
2. **调整口径**：改为 `in_hand` / `on_ear`（数据集里没有"人"的框，不能凭空造）
3. **重训**：`exp6_phone_usage_yolo11s`，40 轮，每轮约 11.7 分钟（batch 4 / workers 2 / imgsz 640）
4. **验收**：以"真实负样本误报率"为核心指标（对应原始报障）

**结果**（见第 11 节详表）：
- 300 张**真实无手机图**上的误报：**67.7% → 1.3%**（conf≥0.5），框尺度从人脸尺度回到手机尺度
- **Precision 0.8251 / Recall 0.3520**（conf=0.50）
- 已接入线上静态 Demo 并上线：<https://wmsisme.github.io/yolo11-campus-phone-detection/demo/>

**过程中处理的工程问题**（详见技术债）：checkpoint 被 `strip_optimizer` 剥离后无法续训（#018）、
推理 imgsz 放大反而更差（#017）、Web Demo 硬编码类别名造成"框手机标成人"的静默错位（#008 同源）。

| **exp6** | **YOLO11s** | **40** | `in_hand` / `on_ear` | **0.6934** | 0.3950 | 0.3646 |
| **exp6**（部署阈值 conf=0.50） | YOLO11s | 40 | 同上 | **0.8251** | 0.3520 | 0.3293 |

**核心验收指标——真实负样本误报率**（300 张数据集自带、标注确认为空的"无手机"图）：

| 置信度 | 旧模型 exp3（污染集） | 新模型 exp6 | 改善 |
|:--|:--|:--|:--|
| conf ≥ 0.25 有误报的图 | 239/300 = **79.7%** | 16/300 = **5.3%** | ↓ 93% |
| conf ≥ 0.50 有误报的图 | 203/300 = **67.7%** | 4/300 = **1.3%** | ↓ 98% |

**框尺度对照**（判断"是否在框人脸"的客观证据）：

| 模型 | 检出框边长中位 | 解读 |
|:--|:--|:--|
| 旧 exp3 | **0.154–0.313** | 人脸/头部尺度（错的） |
| 新 exp6 | **0.017–0.023** | 手机尺度（对的） |

> **补充发现**：对 conf≥0.5 的那 4 张"误报"逐张放大目视核对——**画面里都真的有手机**
> （手握手机 / 竖握白色手机）。即这批"负样本"属**数据集漏标**，真实误报率可能比 1.3% 更低。

### 结果分析

**① 标注质量才是决定性因素（本项目最大教训）**：
- 早期结论"数据量是核心瓶颈"（141 张 → 0.30，合并到 22,879 张 → 0.73）**已被推翻**
- 真相是：合并后的数据集**标注被污染**——"手机"框被大量套在人脸上（语义倒挂：cellphone 框中位边长
  比 People using cellphone 还大）。指标因此虚高，而**实际使用中误报严重**
- 换成干净数据（约 1.7 万张）后，指标数字**看起来变低**（mAP@50 0.365），但**实际效果大幅变好**
  （误报 67.7% → 1.3%）——**指标必须与使用体验一致才有意义**

**② 用对了指标**：原始报障是"把人脸当手机"，对应指标是**误报率 / Precision**，而不是 mAP。
如果只盯 mAP，会得出"新模型退步了"的错误结论。

**③ 阈值与指标的权衡（如实呈现）**：Precision 随阈值单调上升，达标需付代价——

| conf | Precision | Recall | mAP@50 |
|:--|:--|:--|:--|
| 0.25 | 0.6934 | 0.3950 | 0.3646 |
| 0.40 | 0.7737 | 0.3734 | 0.3500 |
| **0.50** | **0.8251** | 0.3520 | 0.3293 |
| 0.70 | 0.9300 | 0.2204 | 0.2120 |

**④ 已验证无效的方向（省得后人重走）**：把推理 `imgsz` 从 640 提到 960/1280 以救小目标——
实测**反而更差**（同一批教室图：640→34 框、960→16、1280→15），因为训练分辨率是 640，改尺寸造成尺度错配。

## 12. 错误分析与经验积累

### 错误 1：旧项目任务-数据不匹配

- **现象**：CLIP 图文检索 Recall@5 = 0.0065
- **原因**：YOLO 目标检测标注被强行用于检索任务
- **教训**：AI 项目的首要问题是"任务-数据"匹配度，模型选择其次

### 错误 2：小样本训练挑战

- **现象**：原始 141 张图片下，三轮实验 mAP@50 仅 0.25~0.30
- **原因**：单一 Roboflow 数据集样本量绝对不足，96 张训练图无法支撑高精度检测
- **对策**：合并 4 个 Roboflow 数据集，扩大数据规模和场景覆盖 → mAP@50 跃升到 0.73

### 错误 3：依赖清理

- **现象**：旧依赖 open_clip_torch、faiss 在新项目中无用
- **对策**：完整重写 requirements.txt

### 错误 4：模型下载网络问题

- **现象**：yolo11s.pt / yolo11m.pt 下载后 zip 损坏
- **原因**：GitHub release 在国内下载不稳定，大文件（>18MB）易损坏
- **对策**：train.py 增加 HF 镜像自动 fallback 机制

### 错误 5：大模型在小数据上的过拟合

- **现象**：yolo11m (150 epochs, 最大模型) mAP@50=0.25，比 yolo11n (0.30) 还差
- **原因**：141 张训练图不足以支撑 20.1M 参数模型的泛化需求，模型越大越容易在小样本上过拟合
- **教训**：大数据 + 小模型 > 小数据 + 大模型。数据量不足时优先扩充数据，而非增大模型

### 错误 6：训练标注污染（本项目最严重的问题）★

- **现象**：线上 Demo 实测「经常把人脸检测为手机」。40 张"无手机"验证图上，conf≥0.25 有 33 张冒出手机框，
  conf≥0.70 仍有 25 张；可视化确认误检框**全部扣在人脸**
- **原因**：重组数据集（22,879 张）的标注被污染——大量 `cellphone` 框套在人脸/头部上。
  证据：`cellphone` 框中 **77.2% 边长 >25%**，而「People using cellphone」中位边长仅 13.5%
  （**语义倒挂**：手机比拿着手机的人标得还大）；42.9% 训练图含这种大框；验证集同源污染 25.1%
- **影响**：mAP@50=0.73 **是虚高的**（照着坏标注考坏标注），且掩盖了"模型在人脸上误报"这一致命缺陷
- **对策**：审计后弃用整个重组数据集，换用干净数据（`phone_usage`）重训（exp6），
  并改用**真实负样本误报率**作为核心验收指标 → 误报 67.7% → **1.3%**
- **教训**：**① 高指标不等于好效果**，必须用与用户目标一致的指标验收；
  **② 换数据前先审标注**——我最初试图"按尺寸丢掉大框"来清洗，实测**污染覆盖全部尺寸档**（连最小档也有人脸误标），
  该方案被证伪；**③ 出图看，别只看统计**——统计只说"42.9% 含大框"，出图才发现连小框也错

### 错误 7：checkpoint 被剥离后无法续训

- **现象**：40 轮训练跑完后想"补到 80 轮"，`--resume` 启动即崩：
  `AssertionError: ...last.pt training to 80 epochs is finished`
- **原因**：训练收尾时 `last.pt` 被 `strip_optimizer` **剥离成推理权重**（`epoch=-1`、优化器状态为空），
  而 `resume_training()` 要求 `0 < epoch+1 < epochs` ⇒ `start_epoch=0` 断言失败
- **教训**：**要支持续训，必须在训练中/收尾前另存一份未剥离的 checkpoint**（`save_period` 定时存）；
  判别只看一条——**ckpt 里 `epoch >= 0` 且带 `optimizer`**，否则只能 warm-start 重训

> 含标注污染 #015/#016、尺度限制 #017、checkpoint 剥离 #018，以及仓库化 #006~#011、静态 Demo #012~#014）

## 13. Harness 作用反思

### 上下文管理

`current-plan.md` 确保了开发进度不被丢失。每次 Agent 工作前读取，完成后更新，避免了"重新开始"的信息断层。

### 工具边界

`SECURITY.md` 明确了 Agent 的操作范围：可修改 src/、tests/、experiments/，不可删除原始数据、不可伪造指标。这些规则在实际开发中有效约束了 Agent 的行为。

### 实验记录

实验记录机制（config.yaml + metrics.json + training_curves.png）确保每组实验可追溯、可复现；
每次换权重、改口径都留下**对照数字**（如误报率 67.7% → 1.3%），而不是只留结论。

### 错误积累

`tech-debt-tracker.md` 将开发过程中遇到的问题系统化记录，避免遗忘，也为最终报告的"错误分析"部分提供了素材。

### 交接机制

`current-plan.md` 中"给下个 Agent 的提醒"部分，使得不同时间、不同 Agent 可以无缝衔接工作。

## 14. 项目局限与改进方向

### 当前局限

1. **目标场景的目标尺度没进训练集**：教室/走廊等**远距离监控视角**下手机只有约 24 像素，
   而训练集以近景/自拍为主 ⇒ 该场景检不出（**尺度/域差异**）。
   已实测**提高推理分辨率无效**（640→34 框、960→16、1280→15，反而更差），只能靠补数据。
2. **不会圈出整个人**：当前口径是"手机的使用状态"（手持/贴耳），**没有"人"的框**——
   训练数据只标了手机。要"框住人"需另找**带人物标注**的数据重训。
3. **召回偏低**：Precision 0.8251 的代价是 Recall 0.3520（conf=0.50 口径）——宁可少报也不乱报，
   属于**有意为之的保守取舍**，但对"尽量找出所有用手机行为"的场景偏弱。
4. **无实时视频流**：仅支持单张图片检测，不支持摄像头实时检测。
5. **网页版模型体积较大**：36.2 MB（yolo11s），首屏下载比旧版（10.1 MB）慢；int8 量化会打坏
   分类头（实测 4 种配置全部失效），故只发行 fp32。

### 改进方向

1. **数据层面（最高优先）**：补"教室/远距离监控视角"的小目标数据；若要框人，则补人物标注
2. **模型层面**：考虑 SAHI（切片推理）等专门处理小目标的方法，而非粗暴提高输入尺寸
3. **应用层面**：接入摄像头实时视频流，支持多路监控
4. **系统层面**：加入行为统计和历史对比，生成周期性分析报告
5. **部署层面**：若在意首屏速度，另训 yolo11n 版（约 3 小时，体积回到约 10 MB）

## 15. 总结

本项目**已作为一个可上线的手机检测系统交付并上线运行**（<https://wmsisme.github.io/yolo11-campus-phone-detection/demo/>），
课程作业只是它的一个侧面。技术上基于 YOLO11，**检测"正在被使用的手机"**（手持 / 贴耳两种状态），
纯前端即可运行（图片不出浏览器）。项目经历了**三个关键阶段**，其中第三阶段最有价值：

**第一阶段**用 Smart School v5（141 张）训练 3 组模型，mAP@50 仅 0.25~0.30。
**第二阶段**合并 4 个 Roboflow 数据集后重训，mAP@50 跃升到 **0.73** —— 当时以为达标了。
**第三阶段（验收→推翻→重建）**：**上线实际使用**时发现「**经常把人脸检测为手机**」，
审计后发现**合并数据集的标注被污染**（大量人脸被标成手机，`cellphone` 框中位尺寸比
"拿着手机的人"还大，语义倒挂）⇒ **0.73 是虚高的**。换用干净数据 + 调整口径后重训（exp6）：

| 指标 | 旧（污染集） | 新（干净集 exp6） |
|:--|:--|:--|
| 真实负样本误报率（conf≥0.5） | **67.7%** | **1.3%** |
| Precision（conf=0.50） | — | **0.8251** |
| 检出框尺度 | 0.154（人脸尺度，错） | 0.017–0.023（手机尺度，对） |

**主要收获**：
1. **高指标不等于好效果**：0.73 的 mAP 掩盖了致命缺陷。指标必须与**用户真实目标**对齐——
   用户的报障是"把脸当手机"，那就该看**误报率**，而不是 mAP
2. **标注质量比数据量更关键**：早期"数据量是核心瓶颈"的结论被推翻；把 22,879 张脏数据换成
   约 1.7 万张干净数据后，指标数字变低而**实际效果大幅变好**
3. **验收要真的用起来**：这个缺陷是在**线上 Demo 实际使用**时才暴露的——所以"自己跑一遍真实路径"
   不是形式，是唯一能发现这类问题的方式
4. **数据-任务匹配是第一性原则**：旧 CLIP 项目失败于任务不匹配；本项目第三阶段失败于**数据不匹配**
5. **Agent Harness 文档体系能有效管理 AI 开发过程**：11 个文档各司其职，进度追踪、错误积累、工具边界各自发挥作用
6. **ultralytics 框架大大降低了目标检测项目的工程门槛**：从数据准备到训练到推理，代码量仅约 1300 行

**与 AI Agent 协作的体会**：
- Agent 在代码生成和文档编写方面效率极高，但需要明确的约束规则（AGENTS.md）引导
- **Agent 会"自信地犯错"，必须用独立性证据兜住**：本次三个典型——把"按尺寸清洗"当解、
  未经验证就建议提高 imgsz、宣布续训成功而未观察真实推进。**都靠实测证据被拦下**
- `current-plan.md` 的"给下个 Agent 的提醒"机制在多轮对话中保证了上下文连续性
- Harness 的最大价值不是"管住 Agent"，而是"**让 Agent 的工作可追溯、可验证**"
